# 運用規約（4 セッション体制）

恒久的な運用の規約・役割・権限・作業の手順の正本。研究の内容は書かない。変更は B が行う（ユーザーの指示による）。

## 1. 正本の所在（同じ情報を 2 か所で管理しない）
| 情報 | 正本 |
| --- | --- |
| 運用の規約・役割・権限・作業の手順 | この文書 |
| 研究目的・ロードマップ・必須の要件・合否の条件・ユーザーの指示 | `docs/notes/111_new_policy_r0_r4.md`（ノート111） |
| 数学的な定式化・設計の仕様 | `design/` |
| 個別のタスク・担当・優先度・状態・依存 | GitHub の Issue（本文とラベル） |
| 技術的な成果物 | コード、研究ノート（`docs/notes/`。書き方は `docs/notes/README.md`、検証の注意は `docs/notes/11_verification_practice.md`） |
| 監修の結果・合否の判定 | 対象の PR・Issue のコメント |
| 重要な研究の状況・ユーザーの判断待ち | Issue #145（ダッシュボード） |

## 2. 役割
| | 役割 | 書く場所 | コメントの先頭 |
| --- | --- | --- | --- |
| A 推進 | 承認された設計に基づく実装・実験・測定・試験・記録（2.1 節） | `basilisk_cupy/`、`cases/`、`tests/`、`docs/notes/`、`README.md` | 【A 推進】 |
| B 統括 | 要求仕様、設計の承認、採否、担当の変更、例外の判断、マージ、Issue の整理 | Issue、この文書、ノート111 の状態と指示の転記 | 【B 統括】 |
| C 監修 | 設計と、実装・実験の結果の、独立の検証と反証（2.1 節） | `audit/` のブランチ（main に入れない）。判定は対象の PR・Issue | 【C 監修】 |
| D 設計 | 定式化、導出、方式の設計、実装と検証の仕様、結果の解釈（2.1 節） | 最上位の `design/` だけ（自己点検のコードは `design/checks/`） | 【D 設計】（方式名の D1・D2 と区別する） |

### 2.1 責務の境界（ユーザーの指示、2026-11-28）
格納する場所ではなく、**作業の中身**で判断する。

**D（設計専任）**
- 主な成果物：数学的な定式化、理論的な導出、方式の設計、実装の仕様、検証の仕様、実験の結果の解釈。
- 設計の自己点検として行ってよいもの（`design/checks/` に置き、設計の根拠として必要最小限にとどめる）：SymPy などによる記号計算、小規模な行列・固有値・特異値の解析、単純化した数学モデルによる安定性の解析、導出した式やアルゴリズムの整合性を確かめる最小限のコード、合成データによる評価式の確認。
- 原則として行わないもの：CFD ソルバーの実装・試作、本格的な数値実験、パラメータの走査、回帰試験の実装、GPU を使う性能の測定、A が担当する実装や実験の先取り、独立の監修の代行。
- 設計の成立を判断するために実際のソルバーによる実験が要る場合は、実験の仕様を書き、Issue を `owner:b` `status:decision` にして、B を介して A に実行させる。

**A（実装・実験専任）**
- 承認された設計に基づく、実装、実験、測定、試験、デバッグ。
- 局所的な実装上の判断と、不具合の原因の分析は行ってよい。**数値の方式そのものの変更や新しい設計は、D に引き継ぐ**（見つけた事実と候補を Issue に書き、`owner:b` `status:decision` にする）。

**C（独立監修専任）**
- D の設計と、A の実装・実験の結果の妥当性を、独立に確かめる。独立の導出、検証のコード、再現の実験、反例の探索は行ってよい。
- D に代わって設計を完成させない。A に代わってライブラリを実装しない（見つけた問題と根拠を書き、直すのは D・A）。

**B（統括）**
- 責務の逸脱を、作業の中身に基づいて監視する。
- モデルの利用枠と計算資源を考えて、D には、高度な理論の推論と設計（その価値のある作業）を優先させる。
- **未レビューの設計の滞留を管理する**：D の設計の先行が、C の監修の処理能力を超えないようにする（`owner:c` `status:review` の設計がたまったら、D の次の設計を `status:backlog` に止めるか、レビューの順を指定する）。

- ユーザーは B だけに指示する。A・C・D への指示は B が Issue に書く。
- **C の技術的な独立性**：C は A・D の仮説や結論に依存せずに検証する。B は C の判定を誘導せず、否定的な判定をそのまま採否に使う。
- 各セッションは自分のクローンで作業する。3 セッション以上が同じ GitHub アカウントで書くので、Approve は使わず、判定はコメントで明示する。

## 3. ラベル
実行タスクには、担当・状態・優先度を **1 つずつ**付ける。担当は「次に作業する人」である。

| 種類 | ラベル |
| --- | --- |
| 担当 | `owner:a`、`owner:b`、`owner:c`、`owner:d` |
| 状態 | `status:backlog`（まだ着手しない）、`status:ready`（着手できる）、`status:doing`（作業中）、`status:review`（担当ラベルの相手のレビュー待ち）、`status:decision`（B の判断待ち。ユーザーの判断待ちは `needs-user` も付ける）、`status:blocked`（ほかの Issue・PR の結果待ち） |
| 優先度 | `priority:p0`（クリティカルパス）、`priority:p1`（待ち時間に進める）、`priority:p2` |
| 種類 | `type:design`、`type:implementation`、`type:experiment`、`type:audit`、`type:epic`（親タスク。実行タスクではない） |
| 段階 | `route:r`（ノート111 の路線） |
| 監修の指摘 | `audit`、`severity:*`（従来どおり） |

- タスクの識別子は Issue の番号である。担当者の名前の付いた番号（A-3 など）は使わない。題名は、解決する技術の課題を書く。
- 親タスク（`type:epic`）は状態のラベルを持たない。
- 使わなくなったラベル（`task`、`gate:*`、`needs-decision`、`resolved` など）は、過去の記録のために残すが、新しく付けない。

## 4. Issue の本文の形式（実行タスク）
目的・背景／要求仕様／作業の範囲／依存／**現在の段階と次の作業**／成果物／事前に確定した合否の条件／完了の条件／打ち切りの条件／関連（設計・PR・ノート）。

- **現行の指示は本文にある。** コメントは、議論・実験の結果・監修の結果・判断の履歴に使う。本文とコメントが食い違う場合は、本文が正しい。指示が変わったら、B が本文を書き換える。
- この文書やほかの Issue の内容を、本文に繰り返さない（リンクで引く）。

## 5. タスクの流れ
重要な数値の方式は、原則として 1 つの Issue で次の段階を進める。段階が進むたびに、**渡す側が**担当と状態のラベルを付け替える。

| 段階 | 担当 | 終わったら |
| --- | --- | --- |
| 1 要求仕様の確定 | B | `owner:d` `status:ready` |
| 2 設計 | D | 「設計確定」（文書とコミットを示す）→ `owner:c` `status:review` |
| 3 設計のレビュー | C | 判定（対象の設計の版 = コミットを書く）→ `owner:b` `status:decision` |
| 4 設計の承認 | B | `owner:a` `status:ready` |
| 5 実装・実験 | A | PR（Issue の番号を書く）→ `owner:d` `status:review`（結果の解釈）→ `owner:c` `status:review` |
| 6 実装のレビュー | C | 判定（対象のコミットを書く）→ `owner:b` `status:decision` |
| 7 採否・マージ・終了 | B | マージして閉じる |

- **引き継ぎのコメント**に書くこと：成果物（コミット・文書・PR）、未解決の事項、次の作業。
- 判定が要修正なら、直す担当（設計は D、実装は A）に `status:ready` で戻す。
- 簡略化：明確な不具合の修正、再現の実験、実験だけの小さいタスクは、設計の段階を省くか、D が基準の確定だけを行う。どちらにするかは、Issue の本文の「現在の段階と次の作業」に B が書く。
- 独立に実行できない作業を、担当ごとに別の Issue に分けない。
- PR にも、Issue と同じ担当と状態のラベルを付ける。

## 6. 定期の確認（A・C・D）
1. 自分のキューを取る。#145 の全文や全ての Issue を読まない。
   ```
   gh issue list --label owner:<自分> --state open --json number,title,labels
   gh pr list --label owner:<自分> --state open
   ```
2. `status:doing` があれば、それを続ける。無ければ、`status:review` → `status:ready` の順に、優先度の高いものから、本文の依存を確かめて 1 つ取り、`status:doing` に変えてから着手する。
   ```
   gh issue edit <番号> --remove-label status:ready --add-label status:doing
   ```
3. 終わったら、成果物と引き継ぎをコメントに書き、5 節の表のとおりにラベルを付け替える。
4. 同時に持つ `status:doing` は 1 件（計算やレビューの待ち時間用に、もう 1 件まで）。ほかの担当が `status:doing` のタスクは実行しない。
5. 取れるタスクが無ければ、何も書かずに終える。**閉じた Issue は読まない。**

B が承認した段階の中の定型の作業（着手、PR の作成、レビュー、ラベルの付け替え）に、B の個別の承認は要らない。B に上げるのは、採否、担当の変更、範囲や基準に関わる疑問、打ち切りの条件に当たった場合で、Issue に「B に求める判断」と書いて `owner:b` `status:decision` にする。待つ間は、依存しないほかのタスクを進める。

## 7. 規則
- **合否の条件は測定の前に Issue の本文に固定し、結果を見てから変えない。** 不成立の結果も、表と試験に残す。
- **ライブラリ本体（`basilisk_cupy/`）を変える PR は、最終のコミットでの全ての試験と、C の判定が必須。** マージは B が行う（A はマージできない）。
- 収束の読み方などの検証の規約は、`docs/notes/11_verification_practice.md` と、ノート111 に従う。
- 指摘は 1 件 1 Issue（PR に対するものは PR のコメント）。場所・問題・根拠・求める対応・重大度と、必須の条件かストレス試験かを書く。
- 意見が割れたら、根拠を付けて反論する。同じ論点で 2 往復しても決着しなければ、B が `needs-user` を付けてユーザーに求める。
- ユーザーの判断を求めるのは：研究目的・必須の要件・合否の基準の変更、方針の根本的な転換、凍結した路線の再開、計画で対処できない重大な問題、重要な設計の判断で合意が得られない場合。B が、選択肢・根拠・推奨・影響を付けて #145 に書く。
- 凍結した路線は再開しない。履歴の書き換え、ブランチやタグの削除、リポジトリの外への公開・送信はしない。Issue は削除せず、閉じて記録に残す（完了は completed、方針の変更・重複・凍結は not planned）。
