# 09 GPU 高速化

- 前提：cupy が numpy より速くなければ意味がない。初版は 0.38 倍（遅い）だった。
- マルチグリッドの内側のループを融合した RawKernel にした（緩和、ゴースト、制限、延長）。`--fmad=false` と演算順序をそろえ、配列版とビット単位で一致させた。
- 1サイクルを CUDA グラフに記録して再生（起動ごとのホスト側 10〜20 µs を除去）。事前確保したバッファだけに書き、Poisson・粘性・欠陥補正の問題オブジェクトを再利用して、グラフを時間ステップをまたいで使い回す。
- fd2 の残差と最大ノルムもグラフ内で計算（atomicMax をビットパターンで使い、厳密）。1反復 = グラフ1回＋8バイト読み出し。
- 実測（RTX 3080 Ti 対 Ryzen 9 5950X の1コア）：CenteredNS N = 512 で 25.8 倍、IMEXBDF2NS（FCCD）N = 256 で 11.0 倍、3D Poisson 128³ で 82.7 倍。
- GeForce では FP64 が FP32 の 1/64 なので、残りのコストは倍精度演算。丸めを変えないため、h や h² での割り算は掛け算に置き換えない。

## 定式化と理論的根拠
GPU の高速化の記録で、数値解析的な主張は少ない。各判断の理由：

- **カーネルの融合と CUDA グラフ**：小さな格子では、1 回の演算の時間がカーネルの起動のホスト側の時間（10〜20 µs）より短い。演算を融合してカーネルの数を減らし、グラフで起動を 1 回にすると、この固定費が消える。
- **ビット単位の一致のための条件**：浮動小数点の演算は結合的でないので、演算の順序と FMA（融合乗加算、丸めが 1 回少ない）の有無で結果が変わる。`--fmad=false` と演算順序をそろえると、配列版とビット単位で一致する。
- **h での割り算を掛け算に置き換えない理由**：`x/h` と `x × (1/h)` は、`1/h` の丸めの分だけ違う。置き換えると、CPU 版・参照値との一致が崩れる。
- **atomicMax をビットパターンで使えば厳密な理由**：非負の IEEE 754 の倍精度は、ビットパターンを符号なし整数として比べた大小が、値の大小と一致する。最大ノルム（非負）の整数の atomicMax は、浮動小数点の最大を厳密に与える。
